# Skill: alembic-migrations

**Tier:** invariant (review, downgrade, no editing applied) · default (naming,
workflow)
**Read when:** changing any model, or writing/reviewing anything in
`alembic/versions/`.

**References**
- Reads: `.claude/docs/design-spec.md` §11 ·
  `conventions.override.md` → section `alembic-migrations`
- Related: `.claude/skills/dal-conventions.md`,
  `.claude/skills/testing-strategy.md`
- Called by: `.claude/commands/build-endpoint.md`
- Enforced by: hook `guard_test_db` (blocks edits to applied migrations)

---

## The three invariants

**1. Autogenerate, then always review.**
Autogenerate is a draft, never a finished migration. It regularly misses
constraint changes, index changes, enum changes, server defaults, and column
type changes that need an explicit cast. It will also happily write a
destructive operation — dropping a column it thinks is gone — without comment.

**Read every generated migration line by line before applying it.**

**2. Every migration has a working downgrade.**
Not `pass`, not a comment. If a change genuinely cannot be reversed — data
destroyed — say so explicitly in the downgrade with a raised error, and record
the one-way nature in `plan/decisions.md`.

**3. Applied migrations are never edited.**
Once applied anywhere, a migration is immutable. Fix forward with a new
revision. Hook-blocked.

---

## Workflow per model change

1. Change the model
2. Autogenerate the revision
3. **Review it** — see the checklist below
4. Apply to the database
5. **Test the downgrade** — apply down, then up again
6. Run the test suite

Step 5 is the one people skip. A downgrade that has never run is a downgrade
that does not work.

---

## Review checklist

Read the generated migration against each of these:

| Check | Why |
|---|---|
| Any `drop_column` or `drop_table` intended? | Autogenerate drops anything it cannot see |
| Column type changes have an explicit cast? | Some engines refuse an implicit cast |
| Nullable → non-nullable has a backfill first? | Will fail on existing rows |
| New non-nullable column has a default or a backfill? | Same |
| Indexes created for new foreign keys? | Autogenerate often misses these |
| Unique constraints correct — partial where soft delete applies? | See below |
| Enum changes handled? | Postgres enums need explicit alteration |
| Server defaults captured? | Frequently missed |
| Naming convention applied to constraints? | Unnamed constraints are undroppable later |
| Does the downgrade actually reverse all of it? | Autogenerated downgrades are often incomplete |

## Soft delete and unique constraints

If a project allows a unique value to be re-used after soft deletion, a plain
unique constraint will block it forever — the deleted row still holds the value.

Use a **partial unique index** that ignores deleted rows. This must be written
by hand; autogenerate will not produce it.

Decide this per table during planning, not when the first duplicate-email bug
appears.

---

## Tenant-scoped tables

Every tenant-scoped table carries `tenant_id`, non-nullable, indexed.

Composite indexes should lead with `tenant_id`, since every query filters on it
first. An index that ignores tenant is rarely used.

Unique constraints on tenant-scoped tables are almost always **scoped to the
tenant** — unique per tenant, not globally. A globally unique constraint on a
tenant-scoped table is usually a bug.

---

## Data migrations

Keep schema changes and data changes in **separate revisions**. A failed data
backfill inside a schema migration leaves the schema half-applied.

Data migrations must be idempotent — safe to run twice. Large backfills run in
batches, not one statement over the whole table.

---

## Naming

Revision messages describe the change in plain terms — what changed and to
what. Not the story ID alone; a migration outlives the story.

Constraint and index naming follows a declared convention set on the metadata,
so constraints have predictable names and can be dropped in a later migration.

---

## Running

Alembic runs **sync** even though the application is async. Two engine
configurations is expected and correct — see `docs/design-spec.md` §5.3.

Everything runs through `poetry run`.

**Never run `alembic upgrade` against anything but the local database.** Blocked
by `guard_bash`. Production migration runs are an operational procedure, not a
development action.

---

## In the inner loop

Model changes during `/build-endpoint` generate a migration, which is reviewed
and applied **before** that endpoint's tests run. Tests execute against the
current schema.

A migration is part of the endpoint's work, not a separate task to batch up
later. Batching means a story's migrations arrive as one large unreviewable
revision.

## Common violations

| Symptom | Fix |
|---|---|
| Autogenerated migration applied unread | Review line by line |
| `downgrade()` is `pass` | Write it, or raise explicitly with a recorded reason |
| Editing a migration that has been applied | New revision, fix forward |
| Non-nullable column added with no default or backfill | Add one |
| Plain unique constraint on a soft-deleted table | Partial unique index |
| Globally unique constraint on a tenant-scoped table | Scope it to the tenant |
| Schema and data change in one revision | Split them |
| Missing index on `tenant_id` or a new FK | Add it |
| Downgrade never tested | Run down then up before moving on |
| Migrations batched at the end of a story | One per model change, in the loop |
